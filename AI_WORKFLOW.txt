# OutZila AI Workflow

## Central Source Order

When sources differ, use this precedence:

1. `OutZila_Blueprint_v1.8.md`, together with `OutZila_Identidade_Autenticacao.md` for identity and signing.
2. `PROJECT_CONTEXT.txt`.
3. `DESIGN_RULES.txt`.
4. `OutZila_Dossier_Produto_Segurador_v0.9.md` for insurance and financial assumptions.
5. The `valuation_matrix` and files in `supabase/migrations/` for implemented behavior, not for overriding later approved strategy.

Use `reference/mockup.png` as the visual authority, not as the authority for catalog scope.

## Implementation Workflow

1. Read `AI_WORKFLOW.txt`.
2. Read the current OutZila Blueprint and identity decision. Historical CleanShare/OutShare documents are not current authority. New Word versions await visual validation; use the current Markdown versions.
3. Read `PROJECT_CONTEXT.txt`.
4. Read `DESIGN_RULES.txt`.
5. Review the relevant valuation matrix and migrations when catalog, eligibility or product positioning is involved.
6. Compare the requested visual scope with `reference/mockup.png` and the current implementation.
7. Analyse the request and identify affected files, content and dependencies.
8. Produce an implementation plan.
9. Wait for explicit user approval before implementation.
10. Implement only the approved scope.
11. Review responsive behaviour, accessibility and existing functionality.
12. Report modified files, relevant selectors and validation results.

## Positioning Consistency Check

Whenever marketplace positioning, categories, eligibility or product scope changes, verify consistency between:

- The latest Blueprint.
- `PROJECT_CONTEXT.txt`.
- `DESIGN_RULES.txt`.
- The `valuation_matrix` and current migrations.
- Public landing-page content.

Resolve or explicitly document any difference between approved strategy and the existing implementation. A documentation-only task must not change HTML, CSS, JavaScript, migrations, matrix files, secrets, DNS, cloud settings or deploy behavior. Do not claim planned Signicat, signatures, payments, deposits or insurance are active.

## Identity Consistency Check

Supabase accounts/login/sessions and Signicat civil identity/signing are separate responsibilities. Support national eID/EUDI Wallet when available and document plus selfie/liveness, NFC when applicable. Never require wallet or CMD as the only launch route. Do not treat email confirmation, user_metadata or pilot access as civil verification. Keep only strictly necessary verified attributes; no default identity-document or biometric retention except documented legal necessity. Bind both verified identities and electronic signatures to each contract and exportable audit trail. Preserve the full identity -> contract -> payment -> bilateral handover -> bilateral return chain. Europe-first is an architecture requirement, not a claim that every provider already processes all data in Europe.

## Approval Rule

Never begin implementation before explicit approval.

Preserve visual fidelity and unrelated functionality. Creating, removing or materially restructuring sections requires an explicit approved request.
